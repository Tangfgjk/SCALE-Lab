# 内容平台与数据接口方案

更新日期：2026-10-13。状态：技术建议。已确认网站与后台同步建设、本地开发后迁移云服务器、中文版优先及后台人员可编辑发布；云服务具体选型和身份认证方式待定。

## 1. 当前状态与目标

当前静态前端使用 `assets/js/data.js`，Express 服务使用 `server/data/content.json`。两份内容并行导致名称、方向和成果可能不一致。下一阶段的首要技术目标是**只有一份可审核的内容来源**，公开页面和 API 从它读取同一版本的数据。

用户已确定网站与内容管理后台同步建设，先在本地开发，再部署到云服务器。可用结构化 JSON 作为迁移和开发种子数据，但交付目标需包含可持久保存、可审核和可发布内容的后台最小可用版本。数据库已确定为 PostgreSQL，本地与云端使用同一引擎；开发环境仍应通过配置切换文件存储和站点地址，为云部署预留迁移路径。云服务商和对象存储方式待选。前端页面与后台围绕同一数据模型并行开发。

## 2. 内容模型的关键修订

所有公开内容类型都应有内容状态（`draft`、`published`、`archived`）、更新时间、最近核验时间与内部来源记录；中英文各有独立的核查状态。首版不强制独立审批人，也不设置必须经过的 `inReview` 内容状态。`published` 仍须满足内容核验规范；单有状态值不足以证明事实真实。

| 类型 | 额外关键字段或区分 |
| --- | --- |
| Member | 双语姓名／简介、公开字段白名单、照片授权、校友去向授权、展示排序 |
| News | 事件日期与发布日期分离、详情内容、来源、双语状态 |
| Publication | 发表阶段（录用、在线发表、正式发表等）、DOI／外链、年份、作者、核验来源 |
| Project | `projectPhase`（计划、在研、结题等）独立于 `publicationStatus`；项目名称与编号均需核验 |
| ResearchDirection | 稳定 ID、双语标题和简介、关联论文／项目、排序 |
| Activity／Asset | 时间、图片说明、版权、人物授权与撤回记录 |
| SiteSetting | 正式名称、Logo、联系渠道、统计数字的口径及核验日期 |

中文内容为首发必填；英文内容可同步录入，但每种语言分别标记草稿与可公开状态。未完成英文审核的内容不出现在英文公开页面，不能通过自动回退拼成中英混杂页面。内部来源和授权记录与公开展示内容分离存储。

## 3. 公开 API 契约

- `/api/v1` 仅返回 `publicationStatus=published` 的内容及已获准公开的字段；详情未发布或已归档时返回 404。
- `/api/v1/home` 只聚合已发布的精选内容。空栏目应按页面规则隐藏，不输出 `@@@`。
- 列表接口定义稳定排序、分页与过滤规则；`status` 参数若用于项目，应明确是 `projectPhase`，不能让访客查询内容草稿状态。
- 统一成功与错误响应格式；文档补充示例、字段含义、空列表行为和版本变更规则。
- 图片 URL 只指向已准许公开的资源，不返回内部授权文件或私人原图路径。

## 4. 后台最小可用范围与权限

后台由管理员和实验室指定的更新发布人员使用，总人数预计不超过 5 人。首版已确认覆盖成员、新闻、论文、项目、研究方向、活动相册和站点设置，均应具备编辑、草稿、预览、发布与撤回流程。图片与授权信息、基础修订历史和操作记录同步纳入；详见[后台功能与管理页面设计](后台功能与管理页面设计_20261013.md)。

权限采用简化的两类账号：**内容管理人员**可编辑、执行发布前检查、发布及撤回内容；**管理员**拥有上述内容权限，并可管理账号。所有获准进入后台的人员均可编辑，编辑者可以自行完成审核发布，无需另设独立 Publisher 角色。即使同一人完成全部步骤，也记录编辑、核查、预览、发布和撤回动作，发布前明确展示来源、授权与语言状态。认证模块设计兼容专用账号和学校统一身份认证，最终登录方案在部署前确定；本地开发同样需要受保护的后台入口。

撤回内容与照片授权需要可操作的下线流程。版本记录至少能说明谁在何时修改了哪些公开字段，并支持恢复先前已审核版本。缓存与静态页面失效方式应随部署方案确定。

## 5. 技术选型的决策点

原设计稿列出的 Next.js／Vinext、D1／R2 仅作历史参考；数据库已确认 PostgreSQL，云服务器已确定为目标部署形态。现阶段先本地开发，不预设云厂商。选型前需确认域名、服务器运维责任、账号登录方式、备份与数据保存要求；再定前端框架、文件存储和缓存时长。

即使继续使用静态 HTML，也能先完成内容统一、审核清单和可核验的公开页面。性能、日志保存期限和备份频率应在部署方案中按实际要求确定，不照搬原稿中的示例数字。

具体逻辑表、索引和版本关系见[数据库结构与发布状态设计](数据库结构与发布状态设计_20261013.md)。

## 6. 实施顺序建议

1. 确认名称、方向与内容公开范围；确定唯一内容结构并清理两份数据差异。
2. 为内容增加发布状态、来源和字段级公开控制；公开 API 与页面读取同一来源。
3. 建立内容校验、预览与发布检查；完成首版页面。
4. 与公开页面同步实现登录、编辑、审核、历史、图片管理与运维能力；上线前完成页面到后台发布内容的端到端验证。
