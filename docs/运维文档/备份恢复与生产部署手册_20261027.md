日期：2026-10-27。云服务器尚未准备，本手册与生产配置已落地；真实域名、证书、公网访问、云备份告警和云端恢复仍待部署后验收。

## 1. 当前目录和资料位置

- 后端 `backend/`，入口 `backend/platform.js`，HTTP app 为 `backend/app.js`。
- 公开站 `frontend/public/`，后台 `frontend/admin/`，浏览器共用代码 `frontend/shared/`。

- 本次备份 `backend/storage/backups/pre-engineering-20261027`。该目录有完整数据库、自有媒体文件和校验清单，含认证及个人资料，不能上传 GitHub。请另外复制到受控备份介质，单机副本不具备异机灾备能力。

## 2. 本地成套备份

`backend/scripts/backup-restore.js` 支持原生 PostgreSQL 客户端，或通过 `--container` 使用现有数据库容器的同版本客户端。

备份前停止本站服务及连接该数据库的其他客户端；工具发现其他客户端连接会拒绝备份。不要停止数据库容器。

```powershell
# 从项目根目录执行，连接信息按本地实际设置
$env:DATABASE_URL='postgres://用户名:密码@127.0.0.1:5433/scale_lab'
node backend/scripts/backup-restore.js backup --container scale-lab-postgres --directory backend/storage/backups/新的唯一目录名
npm start
```

备份目录必须不存在。成功结果包含 `database.dump`、`media/` 和最后生成的 `manifest.json`；没有有效清单的目录不算完成备份。清单包含来源数据库名、Git 提交、逐表数量及内容摘要、数据库备份与逐文件 SHA-256。失败必须查看错误并重新生成新的备份目录。

## 3. 隔离恢复与校验

先创建一个名称不同的空数据库，设置新的空媒体目录。工具拒绝向来源数据库、已有 public 表或非空媒体目录恢复。不会自动清空任何数据库。

```powershell
docker exec scale-lab-postgres createdb -U scale_lab scale_lab_restore_demo
$env:DATABASE_URL='postgres://用户名:密码@127.0.0.1:5433/scale_lab_restore_demo'
$env:MEDIA_ROOT='C:\安全位置\空的恢复媒体目录'
node backend/scripts/backup-restore.js restore --container scale-lab-postgres --directory backend/storage/backups/备份目录名
node backend/scripts/backup-restore.js verify --directory backend/storage/backups/备份目录名
```

`verify` 比对当前连接的目标库与 MEDIA_ROOT，不是只检查备份文件。备份时已确认的 27 张表和 109 个媒体文件在本轮隔离恢复中全部一致。测试恢复后切回正确的环境变量再启动日常网站，避免误连恢复副本。

数据库迁移采用前向兼容方式。应用版本回退使用代码基线与兼容数据库；需要整体恢复时恢复到独立环境再切换，不在生产库执行破坏性回滚。

## 4. 隔离测试与 CI

根目录 `npm run check` 检查正式源码语法。`npm test` 只接受全新、名称以 `_test` 结尾的数据库，自动创建随机测试管理员、独立媒体目录及 4104 测试服务。若测试库已有表，会直接停止，而不是删除资料。下一次复跑应另建空测试库。

GitHub Actions 文件 `.github/workflows/ci.yml` 使用临时 PostgreSQL，执行安装、编辑器构建、官方依赖审计、语法检查、重复迁移、15 组接口测试、生产 Docker 构建和独立容器验收。没有部署服务器凭据，不会连接本地真实数据库，也不会自动更新 gh-pages。

## 5. Linux 云服务器部署步骤

服务器需先安装 Docker Engine 与 Compose，准备域名 DNS 和 80/443 端口。不要开放 PostgreSQL 或直接暴露应用端口；配置中仅代理对外发布 80/443。

```bash
cp infrastructure/.env.example infrastructure/.env.production
# 编辑上述文件：真实域名、独立强数据库密码、匹配且正确 URL 编码的 DATABASE_URL
docker compose --env-file infrastructure/.env.production -f infrastructure/compose.production.yml build
docker compose --env-file infrastructure/.env.production -f infrastructure/compose.production.yml up -d db
docker compose --env-file infrastructure/.env.production -f infrastructure/compose.production.yml run --rm app node backend/db/migrate.js
```

空站点初始化管理员：在当前终端安全设置并 export `ADMIN_LOGIN`、`ADMIN_PASSWORD`，密码至少 12 字符，然后运行：

```bash
docker compose --env-file infrastructure/.env.production -f infrastructure/compose.production.yml run --rm -e ADMIN_LOGIN -e ADMIN_PASSWORD app node backend/scripts/bootstrap-admin.js
docker compose --env-file infrastructure/.env.production -f infrastructure/compose.production.yml up -d app proxy
```

如果要带入本地真实内容，先做成套备份，在全新生产目标恢复，再运行前向迁移；不要重新执行历史导入脚本覆盖人工编辑内容。恢复的本地演示账号必须先改为正式强密码。生产启动会拒绝 `admin`、`123456`、`password` 等已知演示密码；这不代表所有弱口令都能自动识别，账号创建和密码修改仍需遵守强口令规则。

生产容器采用 Node 24、非 root、只读根文件系统、独立媒体卷及临时目录。数据库使用独立网络；只有固定地址的 Caddy 代理可影响转发协议判断。首次部署前确认配置的 `EDGE_SUBNET` 不与服务器现有网段重叠；可以通过 `PROXY_IP`、`EDGE_SUBNET` 改写。

Caddy 根据真实域名申请 HTTPS 证书。应用设置 Secure/HttpOnly/SameSite Cookie、CSRF、CSP/HSTS、持久化登录限流；这不等同于完整的第三方渗透测试。

## 6. 生产备份与恢复工具

提供 `infrastructure/backup.sh` / `restore.sh`，在 Linux 部署主机使用。指定受控的绝对路径环境文件，不把备份写入网站或仓库公开目录。

```bash
export COMPOSE_ENV_FILE=/srv/scale-lab/infrastructure/.env.production
bash infrastructure/backup.sh /srv/scale-lab-backups/一个新的时间目录
```

备份会暂停应用、通过数据库容器导出数据库、通过应用镜像打包媒体、生成 SHA256SUMS/应用提交/完成标记，退出时恢复应用。定时任务应检查退出码、备份生成时间、磁盘空间与远端复制结果；具体频率、保留时间及告警渠道在云环境确定后设置。

恢复工具要求显式指定全新的 Compose 项目、空数据库、空媒体卷。恢复可先在另一台测试主机演练；同机并行恢复还需在独立环境文件设置不同的 EDGE_SUBNET/PROXY_IP，避免网络冲突。不启动代理或占用正式 80/443。

```bash
export COMPOSE_ENV_FILE=/srv/scale-lab/infrastructure/.env.restore
export COMPOSE_PROJECT_NAME=scale-lab-restore-check
export RESTORE_EMPTY_TARGET=yes
bash infrastructure/restore.sh /srv/scale-lab-backups/已完成的备份目录
```

脚本拒绝已有 public 表或非空媒体卷，校验备份文件并检查媒体归档路径；恢复后还要核验内容和图片、应用迁移，并处理演示口令，再考虑切换正式服务。Linux 生产备份脚本本轮仅作语法检查；本地数据恢复使用 Node 工具进行了实际演练，不能将两者混称为云端恢复已通过。
